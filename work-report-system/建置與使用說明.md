# 程優教育科技｜克雷斯技術團隊工作回報系統 · 建置與使用說明

> 目的：讓克雷斯技術團隊（居家辦公）每天自主回報進度，並讓 CEO 一眼判斷「這份回報是不是真的」、「產出量算不算及格」，並直接得到評比等級、工作建議與警示提醒。

這套交付包含六個檔案：

| 檔案 | 用途 |
|---|---|
| `index.html` | 入口頁，兩張卡片分流到回報頁／儀表板；部署平台（含 Manus）指定入口頁時用這個 |
| `report.html` | 克雷斯技術團隊每日回報頁（手機優先，含智慧預設與一鍵複製/延續任務） |
| `dashboard.html` | CEO 儀表板（3D 立體總覽＋評比/建議/警示＋2D 細部圖表） |
| `技術團隊工作回報系統_GoogleAppsScript.gs` | 後端：試算表建置、API、每日計分排程、選用 GitHub 比對（貼到 script.google.com，不隨靜態網站部署） |
| `demo-data.json` | 示範資料，供部署前預覽介面 |
| `README.md` / 本文件 | 部署與操作說明 |

---

## 一、系統怎麼判斷「真假」與「產能」

系統把每一位成員在**過去 7 天滾動窗口**內的回報資料，換算成兩個 0–100 分數：

### 誠信分數（資訊真假的信心指數）
| 子項 | 未接 GitHub 權重 | 已接 GitHub 權重 | 判斷依據 |
|---|---|---|---|
| 證據覆蓋率 | 40% | 25% | **分級計分**，不是單純有/無：附上像網址的連結＝滿分；有填但不是網址（自由文字聲稱）＝0.6；沒連結但誠實寫了原因＝0.4（transparent 但不可驗證）；完全沒填＝0 |
| 時間合理性 | 30% | 20% | 送出時間 vs. 回報的工作日期差距；補登天數越多分數越低，一次補登多天再額外扣分 |
| 內容原創度 | 20% | 15% | **只比對「同一天」內**的任務描述相似度——多日延續同一項工作是正常現象（例如連續 3 天修同一個 bug），不會被誤判成灌水；同一天內出現高度相似的多筆描述，才視為可能的湊筆數訊號 |
| GitHub 客觀佐證 | — | 30% | 回報「已完成/進行中」的工作日，當天是否真的有 commit/PR 紀錄 |
| 主管查核 | 10% | 10% | CEO 在儀表板手動標記「查核未通過」會直接扣該天分數 |

### 產能分數（產出換算成看得懂的分數）
| 子項 | 未接 GitHub 權重 | 已接 GitHub 權重 | 判斷依據 |
|---|---|---|---|
| 加權產出量 | 35% | 25% | Σ(已完成任務的複雜度自評) 對比每人每日預期產出點數 |
| 完成率 | 30% | 20% | 已完成任務 ÷ 總任務數 |
| 準時交付率 | 15% | 10% | 有填「原訂完成日」的任務中準時完成比例 |
| 工時效率 | 20% | 15% | 加權產出量 ÷ 實際工時 |
| GitHub 客觀產出 | — | 30% | commit 數與合併 PR 數 |

### 額外警示旗標（不計入權重分數，但會出現在儀表板警示與任務列表）
| 旗標 | 觸發條件 |
|---|---|
| 缺交N天 | 期間內有幾天完全沒有任何回報（不含請假） |
| 補登 | 送出時間距離回報日期超過 1 天 |
| 重複文字疑慮 | 同一天內任務描述高度相似（原創度 < 70） |
| 證據偏低 | 證據覆蓋率 < 60 |
| 查核未通過 | CEO 手動標記過查核未通過 |
| **內容過於簡略**（新） | 半數以上任務描述少於 8 個字，難以驗證實際做了什麼 |
| **工時落差大**（新） | 期間內預估工時總和與實際工時總和相對落差超過 50%（無論高估或低估） |

### 誠信 × 產能 象限
沿用貴公司「主管人才評比系統」已經在用的 70 分門檻，維持判讀習慣一致：

- 誠信≥70、產能≥70 → **明星型**
- 誠信<70、產能≥70 → **需查核型**（數字好看但可疑，建議實際查核）
- 誠信≥70、產能<70 → **待協助型**（可能卡關，需要幫助而非究責）
- 誠信<70、產能<70 → **高風險型**

所有權重、門檻都寫在 `.gs` 檔開頭的具名常數（`WEIGHTS_AUTH_NO_GH`、`QUADRANT_THRESHOLD`、`MIN_DESC_LENGTH`、`HOURS_VARIANCE_RATIO` 等），可直接修改。**建議先讓團隊試用 1–2 週收集真實資料分佈，再調整權重**，不要一開始就大幅調參。改完權重可執行 `selfTestScoring()`，用寫死的假資料快速核對邏輯有沒有壞掉。

## 二、評比等級／工作建議／警示中心（dashboard.html）

這一層是把上面的分數「翻譯」成 CEO 不用算數學就看得懂的行動指引，全部在前端即時計算，不需要額外部署步驟：

- **評比等級（A+/A/B/C/D）**：以誠信與產能的平均為基礎，兩者落差越大會被額外扣分（避免「誠信超高、產能超低」平均起來看似普通卻掩蓋真實問題）。每位成員的卡片、詳情面板都會顯示一個彩色等級圓章。
- **工作建議**：依象限、旗標、子項分數自動生成 1 級（⚠ 警示，紅/橙底）與 2 級（💡 建議，藍底）的具體行動文字，例如「產出偏低但誠信良好，可能卡關中，建議主動關心並提供協助，而非究責」。規則寫在 `dashboard.html` 的 `generateInsights()`，純前端函式、可直接調整文字或新增規則。
- **警示中心**：HUD 右側「🔔 只看警示」按鈕會顯示目前有幾位成員觸發警示，點下去團隊總覽只顯示這些人；團隊列表預設就依風險排序（高風險型／需查核型排最前面）。
- **團隊排行榜**：團隊總覽面板點「📊 排行榜」展開，把目前篩選範圍內所有成員的誠信/產能分數並排比較，一眼看出全隊相對位置。
- **任務狀態與專案工時分佈**：個人詳情面板新增兩個甜甜圈圖，分別看這段期間任務狀態組成（已完成/進行中/延遲/取消/請假）與工時花在哪些專案上。

## 三、部署步驟（詳細版）

### 1. 建立試算表後端
1. https://script.google.com → 新增專案，貼上整份 `.gs` 內容存檔
2. 執行 `buildSystem` → 第一次會跳出 Google 授權，允許即可
3. 「執行紀錄」會印出試算表網址，打開確認 6 個分頁都建立成功：
   `設定_人員對照`、`每日回報`、`每日查核`、`GitHub活動快取`、`每日分數彙總`、`系統連結`

### 2. 部署為 Web App（必做，無法自動化）
Apps Script 沒有讓程式「自動把自己部署成公開網址」的 API，這步一定要手動點一次：
1. 編輯器右上「部署」→「新增部署作業」
2. 類型選「網頁應用程式」
3. 執行身份：**我**；存取權限：**任何人**
4. 部署後複製 `.../exec` 網址

### 3. 填人員名單
到「設定_人員對照」分頁，刪掉範例列，填入真實成員：姓名、4碼PIN、狀態（在職/停用）。GitHub帳號/監控Repo/個人預期產出點數為選填。

### 4. 接前端
`report.html`、`dashboard.html` 開頭的 `API_URL` 貼上 `.../exec` 網址，重新部署到 Netlify Drop 等平台（見 `README.md`）。

### 5.（選用）設定管理密鑰
在 Apps Script 執行一次：
```js
setAdminKey("你想要的密鑰字串")
```
`dashboard.html` 第一次點「送出」查核標記時會跳出輸入框，貼上同一組字串即可（僅存在瀏覽器 sessionStorage，重開瀏覽器要再輸入一次，不會寫死在檔案裡外流）。

## 四、（選用）啟用 GitHub 交叉比對

如果克雷斯技術團隊的程式碼在 GitHub 上，可以讓系統自動比對 commit/PR 紀錄佐證回報真實性：

1. 到 GitHub 申請一個 Personal Access Token（Fine-grained PAT，權限給要監控的 repo 的 `Contents: Read-only`、`Pull requests: Read-only` 即可）
2. 在 Apps Script 執行一次：
   ```js
   setGithubToken("ghp_xxxxxxxxxxxx")
   ```
3. 回「設定_人員對照」分頁，幫有對應 GitHub 帳號的成員填上「GitHub帳號」與「監控Repo」（格式 `owner/repo`，多個用逗號分隔）
4. 手動執行一次 `syncGithubActivity` 確認「GitHub活動快取」分頁有寫入資料、執行紀錄沒有 401/403（PAT 權限不足）或 404（repo 名稱打錯）
5. 之後系統每天凌晨 2 點自動同步，誠信分數/產能分數會自動切換成「已接 GitHub」的權重表

**PAT 絕對不要貼進 Sheet 儲存格或任何 HTML 檔**——只透過 `setGithubToken()` 存進 Apps Script 的「指令碼屬性」，這是 Google 官方的機密存放區，不會出現在試算表或原始碼裡。

## 五、讓團隊回報更輕鬆（report.html）

- **記住上次選擇**：送出過一次任務後，下次「＋ 新增今日任務」會自動帶入上次用的專案／系統別與複雜度自評，減少重複輸入。
- **複製上一筆／延續任務**：今日已回報清單與待送出草稿，每筆都有「📋 延續這項任務／複製一份」按鈕，點下去會開一張預填專案、描述、複雜度、工時的新表單，只需確認或微調內容再送出——特別適合跨日持續進行的同一項工作，證據連結與完成狀態則刻意不帶入，避免誤用到前一筆的舊資料。
- **簡短描述提示**：任務描述低於 8 個字時，欄位下方會出現「描述有點簡短…」的柔性提示（不會擋住送出），從輸入端就自然提高回報內容的可驗證程度。
- **今日無工作／請假快速鍵**：避免出席熱力圖把請假日誤判成缺交。

## 六、前端技術細節（給之後維護的工程師看）

### CORS 對策
Google Apps Script Web App 有個常見地雷：`fetch()` 送 `Content-Type: application/json` 的 POST 會觸發瀏覽器 preflight（`OPTIONS` 請求），但 Apps Script Web App 對 preflight 的支援不穩定，容易整個送不出去。

本系統的解法：**POST 一律用 `Content-Type: text/plain;charset=utf-8`** 送出 JSON 字串 body，這是瀏覽器 CORS 「安全列表」內的內容類型，不會觸發 preflight；伺服器端 `doPost` 不管宣稱的 content-type，一律 `JSON.parse(e.postData.contents)` 解析。GET 請求（讀取儀表板資料）本來就不需要特殊處理。

刻意**不用** `mode:'no-cors'` 盲送法：那樣完全讀不到伺服器回應，PIN 輸入錯誤、送出失敗都沒辦法回饋給使用者，對一個「在意真實性」的系統來說是不好的取捨。

若實際部署後發現 `text/plain` 方案在某些瀏覽器/網路環境仍讀不到回應，備援方案是改用隱藏 `<iframe>` + `<form target="hidden_iframe">` 的傳統送出法（完全不受 fetch/CORS 規則約束，代價是讀不到伺服器回應內容，UI 只能樂觀假設成功）。

### 示範模式（Demo Mode）
兩個頁面在 `API_URL` 留空時自動切換示範模式：
- `dashboard.html` 直接讀取 `demo-data.json`（內含刻意設計的 5 種典型樣態，方便一次看到所有評比等級、警示與建議文案的實際呈現）
- `report.html` 的登入僅接受示範名單中的姓名（見登入頁下方提示），送出的回報存在瀏覽器 localStorage（`wr_demo_extra_<姓名>`），`dashboard.html` 會自動合併顯示，讓你在本機就能測試「送出回報 → 儀表板即時反映」的完整流程

### 3D 場景與圖表
`dashboard.html` 用 Three.js r128（CDN 載入方式與貴公司現有「主管人才評比系統」的 `index.html` 完全一致，含 jsdelivr 備援）繪製「誠信×產能」象限地板與浮動節點，手勢拖曳旋轉、滾輪縮放、點擊節點下鑽個人詳情。2D 圖表（雷達圖/長條圖/趨勢折線圖/團隊排行榜/狀態與專案甜甜圈圖）用 Chart.js 4，出席熱力圖是純 CSS Grid 自製（不再多引一個函式庫）。3D 場景或 Chart.js 若因網路限制載入失敗，會自動降級成純列表模式或顯示文字提示，不會讓整頁失效——圖表容器改用隱藏＋插入提示文字的方式處理，即使同一張圖表被重複重繪（例如排行榜每次篩選都會重繪）也不會出錯。

## 七、安全檢查清單（部署後務必確認）
- [ ] 試算表**沒有**開啟「知道連結可編輯」給非 CEO 的人
- [ ] `report.html` 的連結只給克雷斯技術團隊，`dashboard.html` 的連結只給 CEO 自己
- [ ] 「設定_人員對照」的 PIN 已從範例值改成真實值
- [ ] `ADMIN_KEY` 已透過 `setAdminKey()` 設定真實密鑰
- [ ] `GITHUB_PAT`（若有啟用）只存在 Apps Script 指令碼屬性，未出現在任何檔案或試算表儲存格

## 八、日常維護
- 想改評分權重或旗標門檻：直接改 `.gs` 檔開頭的常數（`WEIGHTS_AUTH_*`、`WEIGHTS_PROD_*`、`QUADRANT_THRESHOLD`、`MIN_DESC_LENGTH`、`HOURS_VARIANCE_RATIO` 等），改完可執行 `selfTestScoring()` 用假資料快速驗證邏輯沒壞掉，不需要跑完整表單流程。
- 想改工作建議／警示文案：改 `dashboard.html` 裡的 `generateInsights()` 函式，純前端文字規則，不影響分數計算。
- 想重新安裝排程觸發器：執行 `resetTriggers()` 清空後，重新執行一次 `buildSystem()`。
- 每日 23 點左右系統會自動把每人過去 7 天的分數寫入「每日分數彙總」；當天尚未跑到排程前，儀表板會即時現算並標示為「即時」。
